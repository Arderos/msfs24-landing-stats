# Telemetry compression validation

Local work for P10 / LS-010, 2026-10-17. No production format change or deployment.

The candidate is [ZstdSharp.Port 0.8.8](https://www.nuget.org/packages/ZstdSharp.Port/0.8.8),
source commit `2cd0c019693bc786a5fe5c3be94e107b24e7267e` in
[ZstdSharp](https://github.com/oleg-st/ZstdSharp). The benchmark runs its net462
implementation under net48 x64, CLR `4.0.30319.42000`. These are .NET measurements,
not the earlier native Python results.

All 1496 source ZIPs match their inventory SHA-256. All members, totalling
3,792,639,634 uncompressed bytes, survive exact byte roundtrip. The inputs include
147 archives generated by the `0.9.4-live` family. No G17 values, frames, headers,
metadata or decision entries are changed.

Zstd-9 saves 8.00% against existing archives across the full corpus and 11.26%
on the 147 recent archives. Compression is modestly faster in this runtime;
the previous native benchmark's twofold speedup does not apply. Many old captures
are very small, so the full-corpus median does not describe a normal landing.

Zstd-19 was separately run on the same deterministic 36-archive sample as the
earlier study. All bytes roundtrip. The sample saves 27.77%; its 12 recent archives
save 28.36% with 1,019.80 ms median encoding and 4.05 ms median decoding. This is
not a full-corpus Zstd-19 result. Level 9 remains the candidate for normal capture
packaging; the more expensive level is not needed for the runtime refactor.

Sizes normalize compressed members to the same ZIP envelope; a new versioned
format's manifest overhead has not been included. The Deflate baseline differs
slightly from existing ZIP bytes and is reported separately. Timings exclude CSV
serialization and input I/O. Process CPU also includes source decompression and
byte comparison; the first codec invocation includes JIT cost. The probe holds
source and restored members in memory: process peak working set was 442.6 MB for
Zstd-9 and 656.8 MB for Deflate. These peaks are not a production streaming bound.

The probe rejects source members over 256 MiB, caps decoded output at the exact
source length, and sets the Zstd decoder window limit to 128 MiB. Production
validation must use the receiver's stricter configured aggregate limit, bounded
streaming, an execution deadline, strict manifest/hash checks and malformed input
tests. A stronger codec must not silently inherit the legacy 25:1 ratio limit:
the previously reproduced `60031d1a…` case still needs an explicit new-format
policy. Existing ZIP validation must retain its current rules.

The implementation now includes a [versioned container](capture-archive-format.md),
shared netstandard2.0 reader/writer, Python receiver/dashboard reader and
capability-gated production writers. Both platforms check lengths, hashes,
framing and resource bounds. New-format retries retain identical bytes; unknown,
expired or downgraded receivers select legacy format for future captures and
retain existing new-format files pending. Receiver deployment remains a separate
release gate and has not occurred.

Final-container verification examined all 1496 original inventory hashes. Of
these, 1495 roundtrip byte-for-byte on net48, net10 and Python. One intentionally
invalid fixture (`3e4556ad…`, `server/bytes_4194305/bug-report.zip`) has a 4 MiB + 1
decision journal and is rejected by the documented bound; it is retained unchanged.
The 1495 actual containers total **780,993,510 bytes**, versus **848,143,143** original
bytes, a **7.92% reduction including the descriptor and ZIP wrapper**.

The final streaming net48 corpus process peaked at 56,299,520 bytes working set;
the net10 read/compare process peaked at 98,906,112 bytes. These are library/corpus
process measurements, not a claim about total WPF/recorder memory. Repacking
resumed after a bound check, so its total elapsed time is not a fresh encoding
benchmark; use the controlled measurements above for codec timing comparisons.

The full Python comparison found no unexpected differences: 1478 archives have
identical accepted receiver facts, 13 remain rejected, and four valid repetitive
archives become accepted under format 2's explicit resource bounds instead of
the old ratio rule. The dashboard produces identical normalized content for 1494
archives; its existing malformed-telemetry fixture is rejected in both formats.
All originals retain their inventory hashes. The comparison took 453.52 seconds.
Evidence: `receiver-corpus-results.json`, `receiver-corpus.log`,
`net48-final-corpus.log` and `net10-final-corpus.log`.

The application suite after format integration and the legacy-worker quota gate
passed all **277** checks (`p10-storage-full-tests.log`). All **121** receiver tests
passed with both real net48 format/provenance fixtures enabled
(`server-all-fixtures-tests.log`). The separate codec test also ran inside the
actual isolated WorkerHost with its own configuration; no application-domain
binding assumptions were required (`isolated-codec-tests.log`). Protocol
roundtrips, including endpoint capability observations and the runtime quota
handshake, passed on net48 and net10 with unchanged numeric identity.
