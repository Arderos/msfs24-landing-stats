## Критичные (потеря данных)

### 1. Удаление папки/файлов в Drive массово удаляет локальную историю
**Файл:** `src/LandingStats.App/GoogleDrive/GoogleDriveBackupService.cs:404`

Любой файл посадки, помещённый в корзину на стороне Drive, трактуется как удаление, инициированное приложением, и молча удаляет локальную запись. Перемещение в корзину всей папки «Landings» удаляет **всю** локальную историю. Корневая папка защищена через `ResetForRoot`, но папка Landings и отдельные файлы — нет.

**Сценарий:** пользователь наводит порядок в Drive и удаляет папку «Landings», полагая, что локальные копии в безопасности. Drive помечает всех потомков `trashed=true`, фильтр `Active()` их отбрасывает, и каждая локальная посадка со ссылкой в state попадает в ветку удаления: `_landings.Delete(pair.Key)` выполняется для всех без подтверждения. Восстановление — только из корзины Drive в течение 30 дней.

### 2. Двустороннее расхождение одной посадки навсегда блокирует всю синхронизацию
**Файл:** `src/LandingStats.App/GoogleDrive/GoogleDriveBackupService.cs:362`

Если локальная и облачная копии одной посадки разошлись одновременно, при каждой синхронизации выбрасывается `InvalidDataException` («both were changed») без пути разрешения конфликта. Исключение прерывает весь `SyncAsync`: остальные посадки и настройки больше не синхронизируются никогда.

**Сценарий:** посадка записана на устройстве A, синхронизирована на устройство B ещё как «Unknown airport»; затем `LoadHistory`/`TryResolveAirport` на обоих устройствах разрешают аэропорт по разным кэшам facilities (или будущая версия приложения пересериализует записи иначе — ср. пересохранение в `SelectRecord`/`RefreshRawPitchInputSelection`). `localHash`, `remoteHash` и `link.Sha256` различаются, и UI вечно показывает «Sync failed · Local and cloud landing <guid> were both changed», пока пользователь не догадается удалить посадку на одном из устройств.

## Высокая серьёзность

### 3. Вход в Google без отмены и таймаута навсегда блокирует кнопки Drive
**Файл:** `src/LandingStats.App/MainWindow.xaml.cs:831`

Если пользователь закрыл вкладку браузера, не подтвердив доступ, `LocalServerCodeReceiver` слушает loopback-порт бесконечно (отмена только через `_lifetimeCancellation` при закрытии окна). `SignInAsync` не возвращается, `finally` не выполняется, `_googleDriveOperationBusy` остаётся `true` — секция Drive висит в состоянии «Synchronizing…» (текст, к тому же, неверный для входа), все три кнопки отключены до перезапуска приложения.

### 4. Локальное удаление посадки завязано на инфраструктуру Google Drive даже без входа
**Файл:** `src/LandingStats.App/GoogleDrive/GoogleDriveBackupService.cs:56`

`OnConfirmDeleteLandingClick` всегда идёт через `DeleteLandingAsync`:
- если `_stateRepository.Save` бросает исключение (диск заполнен, антивирус держит `.tmp`) — локальное удаление отменяется с ошибкой, хотя раньше записи были «локальные и переносимые»;
- если идёт сетевая синхронизация, диалог подтверждения висит с отключённой кнопкой без обратной связи, пока синхронизация не закончится;
- для пользователей, никогда не подключавших Drive, каждый удалённый id добавляется в `PendingDeletes` и не удаляется никогда (очищают только `SyncAsync` и `ResetForRoot`) — список растёт неограниченно.

### 5. Лаунчер требует «ровно те же файлы» в runtime-каталоге
**Файл:** `src/LandingStats.App.Launcher/Program.cs:282`

`RuntimeIsComplete` теперь через `SetEquals` требует точного совпадения набора файлов (исключение — только `.bootstrap`). Любой посторонний файл (`desktop.ini`, остатки антивируса/индексатора, случайный `.tmp`) вызывает полное удаление и переизвлечение при каждом запуске; а если DLL заблокированы работающим экземпляром, `Directory.Delete(..., true)` бросает `IOException` до `Main`, и пользователь видит «MSFS Landing Stats could not start». Старая проверка `RequiredFiles.All()` эти случаи переносила.

### 6. Сервисы Drive могут быть уничтожены во время активной синхронизации
**Файл:** `src/LandingStats.App/MainWindow.xaml.cs:2033`

Защита при закрытии окна проверяет только `_googleDriveSyncTask`/`_googleDriveDeleteTask`, но стартовая синхронизация (`OnWindowLoaded`) и синхронизация по кнопке SYNC NOW в `_googleDriveSyncTask` не записываются. При закрытии окна во время такой синхронизации `GoogleDriveBackupService`/`GoogleDriveApiClient`/`GoogleOAuthClient` уничтожаются на лету: `SemaphoreSlim.Release` в `finally` бросает `ObjectDisposedException`, `HttpClient` умирает посреди запроса, сохранение state пропускается. Правильнее опираться на счётчик `_googleDrivePendingOperations`, который учитывает все синхронизации.

## Средняя серьёзность

### 7. Синхронизация делает O(n²) обходов файловой системы
**Файл:** `src/LandingStats.App/GoogleDrive/GoogleDriveBackupService.cs:271`

Каждая синхронизация вычисляет `GetBackupFingerprint` для каждой локальной посадки, а каждый вызов запускает `Directory.EnumerateFiles` в `FindRecordPath`. При нескольких сотнях записей — сотни обходов каталога на каждую синхронизацию (которая ставится в очередь после каждой сохранённой посадки и каждого изменения настроек), причём внутри блокировки `_landingRepositoryGate`, конкурирующей с `LoadHistory`/`SelectRecord` на UI-потоке. Достаточно одного обхода каталога в карту id→путь на синхронизацию.

### 8. `IsSignedIn` расшифровывает токен через DPAPI при каждом вызове на UI-потоке
**Файл:** `src/LandingStats.App/GoogleDrive/GoogleOAuthClient.cs:28`

`IsSignedIn` → `GoogleOAuthTokenStore.HasRefreshToken` читает файл токена, декодирует Base64 и вызывает `CryptUnprotectData` при каждом вызове. Вызывается из `RefreshGoogleDrivePresentation` (каждая смена языка, открытие настроек, каждый `RefreshLocalizedPresentation`) и из `QueueGoogleDriveSync` (каждая сохранённая посадка) — всё на dispatcher-потоке. Хранилище токена владеет `Save`/`Clear`, поэтому состояние входа можно кэшировать в памяти и инвалидировать при `Save`/`Clear`.

### 9. Автозапуск инициализируется только после полной сетевой синхронизации
**Файл:** `src/LandingStats.App/MainWindow.xaml.cs:167`

`OnWindowLoaded` ждёт завершения полной синхронизации с Drive перед `InitializeAutoStartSetting`. При медленном или недоступном Drive интеграция с `exe.xml` не проверяется/не применяется и первый диалог автозапуска не показывается — потенциально минуты. Синхронизация не обязана предшествовать автозапуску: изменения из облака и так согласуются последующим `InitializeAutoStartSetting`.

### 10. Escape во время отложенного удаления ломает состояние диалога подтверждения
**Файл:** `src/LandingStats.App/MainWindow.xaml.cs:497`

`HideDeleteLandingConfirmation` (доступно по Escape/Cancel, пока удаление ждёт гейт синхронизации) заново включает кнопку Confirm и очищает `_pendingDeleteRecord` при активном удалении. Сценарий: пользователь подтверждает удаление записи A, пока гейт занят синхронизацией, жмёт Escape, открывает диалог удаления записи B — завершение удаления A вызывает `HideDeleteLandingConfirmation` и закрывает диалог B до действия пользователя; а если B уже подтверждена — два удаления переплетаются и путь завершения A сбрасывает состояние, от которого зависит B.

## Низкая серьёзность

### 11. Дублирующее состояние занятости и лишний Interlocked
**Файл:** `src/LandingStats.App/MainWindow.xaml.cs:881`

`_googleDriveOperationBusy` дублирует состояние, выводимое из `_googleDrivePendingOperations`; `Interlocked` применяется к счётчику, который трогается только на dispatcher-потоке. Два поля приходится согласовывать между путями инкремента/декремента `RunGoogleDriveSyncAsync` и ручной установкой в `OnGoogleDrivePrimaryClick`. «Занято» можно свести к `_googleDrivePendingOperations > 0` (плюс флаг входа), убрав избыточное состояние.

## Как исправлено (ключевое)

1. **Drive больше не авторитет для удалений.** Локальная посадка, отсутствующая в облаке, теперь **загружается заново**, а не удаляется ([GoogleDriveBackupService.cs:463-478](src/LandingStats.App/GoogleDrive/GoogleDriveBackupService.cs#L463-L478), с явным комментарием). В облако удаление попадает только через `PendingDeletes` от явного удаления в приложении. Покрыто тестом «only propagates in-app deletes».
2. **Конфликты посадок не роняют синхронизацию.** Вместо исключения — `result.ConflictedLandingIds` и жёлтое предупреждение с количеством в UI; остальные посадки и настройки синхронизируются. Плюс добавлен автослияние метаданных (`TryResolveLandingMetadataConflictAsync` + `MetadataNeutralHash`): расхождение только в аэропорте/ВПП/дистанции (тот самый сценарий с разными кэшами facilities) сливается автоматически. Покрыто двумя тестами.
3. **Вход:** таймаут 3 минуты через `CancelAfter`, кнопка Disconnect во время авторизации превращается в Cancel ([MainWindow.xaml.cs:884-928](src/LandingStats.App/MainWindow.xaml.cs#L884-L928)), отдельный текст состояния «Authorizing».
4. **Удаление разделено:** локальное удаление выполняется сразу (`DeleteLandingLocally`, для неподключённых пользователей — напрямую через репозиторий, без Drive-состояния вообще); запись в `PendingDeletes` — отдельным шагом после закрытия диалога, её ошибка показывается только как ошибка Drive. Покрыто тестом «does not require Google Drive state storage».
5. **Лаунчер:** возвращена проверка «все нужные файлы существуют и непустые», посторонние файлы допускаются ([Program.cs:264-281](src/LandingStats.App.Launcher/Program.cs#L264-L281)).
6. **Закрытие окна:** защита теперь `!GoogleDriveBusy && …`, где `GoogleDriveBusy` опирается на счётчик `_googleDrivePendingOperations`, инкрементируемый каждой синхронизацией до первого await; при активной операции dispose пропускается (процесс всё равно завершается).
7. **Фингерпринты:** `GetBackupFingerprints` строит набор путей одним `EnumerateFiles` на всю пачку ([LandingRepository.cs:183-215](src/LandingStats.App/Storage/LandingRepository.cs#L183-L215)). Покрыто тестом «lightweight fingerprint».
8. **Токен:** `HasRefreshToken` кэширует результат, инвалидация в `Save`/`Clear`/`Load`; DPAPI-расшифровка происходит только при реальной работе с токеном.
9. **Автозапуск:** `InitializeAutoStartSetting()` вызывается до `await` синхронизации ([MainWindow.xaml.cs:171-179](src/LandingStats.App/MainWindow.xaml.cs#L171-L179)).
10. **Диалог удаления:** закрывается принудительно в том же обработчике до асинхронной части; Escape блокирован при `_deleteLandingInProgress`; завершение удаления больше не трогает UI диалога.
11. `_googleDriveOperationBusy` удалён; занятость — вычисляемое свойство `GoogleDriveBusy => _googleDriveAuthorizing || _googleDrivePendingOperations > 0`, `Interlocked` убран.

## Оставшиеся замечания (не блокирующие)

- **Конфликт настроек «both changed» по-прежнему бросает исключение** ([GoogleDriveBackupService.cs:728](src/LandingStats.App/GoogleDrive/GoogleDriveBackupService.cs#L728)) — это теперь осознанный fail-safe (есть тест «concurrent settings edits fail without data loss»), но пути разрешения у пользователя нет: если настройки изменены на двух устройствах между синхронизациями, каждая синхронизация будет заканчиваться ошибкой, пока локальные настройки случайно не совпадут с облачными. Настроек мало (язык, автозапуск), так что вероятность и цена невысоки, но стратегия разрешения (например, по последнему изменению) была бы уместна. Побочный эффект: в такой ситуации `Save(state)` в конце `SyncAsync` пропускается, и ссылки посадок пересчитываются заново при каждой синхронизации (без потери данных).
- **Узкое окно «воскрешения» удалённой посадки:** `PendingDeletes` персистится только после захвата `_syncGate`. Если пользователь удалил посадку во время долгой синхронизации и закрыл приложение до её завершения (или `Save` состояния упал), локальная копия уже удалена, а запись об удалении не сохранена — при следующей синхронизации посадка вернётся из облака. Для «Drive — это бэкап» это безопасное направление ошибки (данные возвращаются, а не теряются), но поведение может удивить.

## Дополнительный проход по оставшимся замечаниям

Оба остаточных сценария после повторной проверки также устранены:

- конфликт настроек больше не бросает повторяющееся исключение: устройство, выполняющее конфликтующую синхронизацию, публикует локальный набор настроек одной новой ревизией, после чего другие устройства скачивают её и сходятся;
- `PendingDeletes` записывается атомарно без ожидания сетевого `_syncGate`, а финальная запись состояния синхронизации сохраняет удаления, поставленные в очередь параллельно. Закрытие приложения во время долгого Drive-запроса больше не оставляет удаление только в памяти.

Оба поведения закреплены регрессионными тестами: конфликт настроек проверяется до полного схождения двух клиентов, а тест удаления проверяет наличие durable `PendingDeletes` до разблокировки активной синхронизации.
